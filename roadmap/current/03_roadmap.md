# 開発ロードマップ

> 関連: [00_overview.md](./00_overview.md) | [02_current_status.md](./02_current_status.md) | [04_tech_stack.md](./04_tech_stack.md) | [05_infrastructure_cost.md](./05_infrastructure_cost.md)

本ロードマップは Issue #1 でのコードレビュー結果およびオーナーフィードバックを反映している。

## インフラ戦略

段階的スケールの方針:

1. **Stage 1 (現在)**: 自宅端末 (16GB RAM) + Faster Whisper (CPU) で開発・効果見極め
2. **Stage 2**: 効果確認後、外部 VPS (CPU) へ移行し安定運用
3. **Stage 3**: GPU インスタンスへ移行、モデル大型化で高精度化

Phase 1-3 は Stage 1 (自宅CPU) で完結させ、Phase 4-5 の負荷状況を見て Stage 2-3 へ移行する。

## フェーズ構成

```
Phase 1: 基盤安定化 + Faster Whisper 移行
    |  ← Stage 1: 自宅端末 (16GB RAM, CPU)
Phase 2: コア機能完成 (UI・WebSocketサービス)
    |
Phase 3: データ永続化・管理機能
    |
Phase 4: 高度な音声分析機能 (後処理)
    |  ← Stage 2 検討: 外部 VPS (CPU) へ移行
Phase 5: 音声変換・キャラクター再生 (後処理)
       ← Stage 3 検討: GPU インスタンスへ移行
```

### Faster Whisper 移行の詳細

| 項目 | 変更内容 |
|---|---|
| パッケージ | `openai-whisper` + `torch` → `faster-whisper` (CTranslate2ベース) |
| メリット | CPU推論が 4〜8倍高速、メモリ使用量大幅削減 |
| CPU対応 | `compute_type="int8"` で16GB RAMマシンでも small モデルがリアルタイム処理可能 |
| 影響範囲 | `whisper.py` のモデルロード・推論呼び出し部分を書き換え |
| モデル互換 | Whisper互換モデルをそのまま使用可 (tiny, base, small, medium, large-v3) |

### Faster Whisper でのモデル別CPU性能見込み (16GB RAM)

| モデル | メモリ使用量 | 1秒音声の推論時間 (CPU, int8) | リアルタイム可否 |
|---|---|---|---|
| tiny | ~0.5GB | ~0.1秒 | 余裕 |
| base | ~0.5GB | ~0.2秒 | 余裕 |
| **small** | **~1GB** | **~0.5秒** | **可能 (推奨)** |
| medium | ~3GB | ~1.5秒 | ギリギリ〜不可 |
| large-v3 | ~6GB | ~4秒 | 不可 |

**Phase 1 の目標モデル: small (int8)** — 精度とCPU性能のバランスが最適。

## Phase 4: 高度な音声分析機能 (後処理)

オーナーの将来ビジョンに基づく高度な分析機能群。
**全て後処理 (非リアルタイム) として実装し、CPU環境での実現を優先する。**

### 4-1: トピック検出

- 録音完了後、文字起こしテキストからトピックを分類
- LLM (大規模言語モデル) による要約・トピック抽出
- トピック遷移のタイムライン表示

### 4-2: 話者特定 (Speaker Diarization) — 後処理

- 録音データを後処理で解析し、話者を自動識別
- 話者ごとに文字起こしテキストを分離表示
- 話者プロファイルの登録・学習
- **CPU後処理**: 1分の音声に対し2〜5分程度の処理時間を許容

### 4-3: 感情認識 — 後処理

- 録音データをバッチ処理で解析し、感情を推定
- 感情メタデータ (喜怒哀楽・興奮度など) の付与
- 感情の時系列変化の可視化
- **CPU後処理**: 音声特徴量抽出をバッチで実行

### 技術的検討事項

| 機能 | 候補技術 | CPU後処理での実現性 | 備考 |
|---|---|---|---|
| トピック検出 | OpenAI API / ローカルLLM | 高 | テキストベースなので軽量 |
| 話者特定 | pyannote.audio / resemblyzer | 中 | 時間はかかるが実行可能 |
| 感情認識 | SpeechBrain / Wav2Vec2 | 中 | バッチ処理で対応可能 |

## Phase 5: 音声変換・キャラクター再生 (後処理)

感情メタデータを含めた音声変換と任意キャラクターでの再生機能。
**後処理で事前生成し、再生時には生成済み音声を使用する。**

### 構想

- 文字起こしテキスト + 感情メタデータを入力として音声合成
- 任意のキャラクターの声質で再生
- 感情を反映した自然なイントネーション生成
- **CPU後処理**: 生成に時間がかかっても、再生前に完了していれば問題なし

### 技術的検討事項

| 機能 | 候補技術 | CPU後処理での実現性 | 備考 |
|---|---|---|---|
| 音声合成 (TTS) | VOICEVOX / Style-Bert-VITS2 / XTTS | 中 | CPU生成は遅いが可能 |
| 声質変換 | RVC / so-vits-svc | 中 | バッチ変換で対応 |
| 感情制御 | スタイルベクトル / プロンプト制御 | TTSモデル依存 | |

### Stage 3 移行判断ポイント

Phase 5 の後処理時間がユーザー体験を損なうレベルになった場合:

- GPU VPS (RunPod L4 等) へのオンデマンド移行を検討
- モデルも small → medium → large-v3 へ段階的に大型化
- 後処理のバッチジョブをGPUインスタンスで実行し、完了後にシャットダウンするコスト最適化運用
